# 072 Wrinkle-First 접근 하이어라키 재설계

## 1. 목적
- 몇 개월 뒤에도 `Skin_wrinkle_proj`의 실험축, 기준 문서, 대표 `config`, `script`, `outputs`, `checkpoints`를 쉽게 찾을 수 있도록 `wrinkle` 중심 접근 하이어라키를 설계한다.
- 실제 실행 경로와 산출물 경로를 바꾸지 않고도, 다시 프로젝트에 진입하는 사람이 빠르게 구조를 이해할 수 있는 접근용 문서 계층을 만든다.
- `Skin_Project` 상위 문서는 실행 대체 구조가 아니라 `wrinkle` 실험축으로 들어가는 인덱스 역할을 하도록 정리한다.

## 2. 앞선 프로세스와의 정합성
### 2-1. 프로세스 1과의 정합성
- `Skin_wrinkle_proj`, `Skin_diagnosis_proj`, `skin_crop_data`는 현재 자산으로 유지한다.
- `Skin_Proj`는 archive 후보지만, 즉시 대규모 이동이나 삭제는 하지 않는다.
- 현재 `wrinkle`, `diagnosis` 모두 절대경로 또는 위치 의존이 있으므로 무리한 물리 이동은 금지한다.
- 다만 프로젝트 구조 재편의 기준점은 `Skin_wrinkle_proj`이며, `Skin_diagnosis_proj`는 이번 구조 설계에서 참고/보조 자산으로 다룬다.

### 2-2. 프로세스 2와의 정합성
- [070_상위_하이어라키_설계_초안.md](./070_상위_하이어라키_설계_초안.md)는 목표 상위 구조를 정의한 문서다.
- 본 문서는 그 목표 구조를 `wrinkle-first` 접근 방식으로 다시 읽는 방법을 정리한다.
- 즉 `070`이 목표 구조 문서라면, 본 문서는 몇 달 뒤 다시 진입할 때 `wrinkle` 기준으로 어디를 먼저 봐야 하는지 정리한 접근 문서다.

### 2-3. 프로세스 3과의 정합성
- [071_wrinkle_프로젝트_상위_편입_규칙_초안.md](./071_wrinkle_프로젝트_상위_편입_규칙_초안.md)에서 `Skin_wrinkle_proj`는 현재 위치 유지가 원칙으로 정리되었다.
- 본 문서는 그 원칙을 유지한 채, 상위 `docs/current/wrinkle` 아래에 접근용 인덱스를 어떻게 설계할지 정리한다.
- 따라서 프로세스 4는 프로세스 3을 뒤집는 문서가 아니라, `wrinkle` 실험축 기준 접근 하이어라키를 만드는 문서다.
- 또한 이번 문서는 `diagnosis`를 대칭적 핵심축이 아니라 후순위 참고 프로젝트로 위치시킨다.

## 3. 핵심 원칙
- `Skin_wrinkle_proj` 본체는 이동하지 않는다.
- 실행 파일과 산출물은 현재 위치에 둔다.
- 상위 `docs/current/wrinkle` 아래에는 실행 대체 구조가 아니라 접근용 인덱스와 안내 문서만 만든다.
- 하이어라키 단위는 폴더명이 아니라 `주름 실험축`이다.
- `diagnosis`는 이번 하이어라키의 중심이 아니라 참고 프로젝트로 둔다.

## 4. 접근 하이어라키 구성 단위
- 이마 주름 중증도
- 미간 주름 중증도
- 오른쪽 눈가 주름 중증도
- 왼쪽 눈가 주름 중증도
- 오른쪽 눈가 주름 상태
- 왼쪽 눈가 주름 상태

## 5. 각 실험축 인덱스 문서에 포함할 것
- 기준 문서
- 대표 `yaml`
- 대표 `script`
- 대표 `outputs`
- 대표 `checkpoints`
- 현재 판단 기준
- 다음에 이어서 볼 포인트

## 6. diagnosis 처리 원칙
- `Skin_diagnosis_proj`는 동급 중심 프로젝트로 두지 않는다.
- 참고용, 보조용, `legacy-project` 성격으로만 정리한다.
- 이번 단계에서는 물리 이동하지 않는다.

## 7. 이동 시 영향받는 경로 체크리스트
### 7-1. config
- `config`와 `configs`가 동시에 존재하는지 확인
- 실제 사용 설정이 어디에 있는지 확인
- yaml 내부 절대경로 존재 여부 확인
- 실행 스크립트가 특정 설정 파일명을 직접 기대하는지 확인

### 7-2. script
- `Set-Location`
- `PYTHONPATH`
- 프로젝트 루트 절대경로
- `SKIN_CROP_ROOT`
- 로그 파일 출력 위치
- checkpoint 저장 위치

### 7-3. import
- `src` 기준 import 경로가 현재 프로젝트 루트를 전제하는지 확인
- 스크립트가 실행 위치에 따라 import가 달라지는지 확인
- `__init__.py`와 패키지 루트가 이동 후에도 같은 의미를 가지는지 확인

### 7-4. outputs
- metrics csv 위치
- predictions 위치
- reports 위치
- confusion matrix 위치
- 웹 PoC에서 직접 참조할 산출물의 경로 고정 여부

### 7-5. docs link
- GitHub 상대경로 유지 여부
- 로컬 절대경로 링크 제거 여부
- current/legacy 문서 간 연결 유지 여부
- 상위 hierarchy 문서와 하위 프로젝트 문서 간 링크 일관성

## 8. 이번 단계에서 하지 않는 것
- `Skin_wrinkle_proj` 이동
- `Skin_diagnosis_proj` 이동
- `skin_crop_data` 이동
- `outputs/checkpoints/logs` 이동
- `scripts/src/configs` 재배치

## 9. 완료 기준
- 상위 `docs/current/wrinkle` 아래에 주름 실험축별 접근 구조가 정의된다.
- 몇 달 뒤 다시 와도 어디서부터 읽고 무엇을 참조해야 하는지 바로 알 수 있다.
- 실제 실행 경로와 산출물 경로는 전혀 깨지지 않는다.

## 10. 한 문장 요약
- 프로세스 4의 핵심은 `Skin_wrinkle_proj`를 기준 프로젝트로 삼고, 상위 `docs/current/wrinkle` 아래에 실험축별 접근 인덱스를 설계해 몇 달 뒤에도 쉽게 프로젝트를 재진입할 수 있게 만드는 것이다.

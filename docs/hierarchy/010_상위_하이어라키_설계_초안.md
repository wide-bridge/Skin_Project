## 4. 상위 폴더 역할 정의
### 4-1. `docs`
- 피부 분석 플랫폼 전체의 상위 문서 허브를 둔다.

세부 역할:
- `docs/current`
  - 전체 프로젝트 기준 문서의 최신본을 둔다.
- `docs/legacy`
  - 상위 차원의 과거 의사결정, 폐기된 방향, 이전 구조 문서를 둔다.
- `docs/hierarchy`
  - 전체 과제 체계, 폴더 설계, 책임 분리, 이행 계획 같은 메타 구조 문서를 둔다.

한 문장 책임:
- `docs`는 **프로젝트 전체 기준과 구조 원칙을 설명하는 상위 문서 계층**이다.

### 4-2. `shared`
- 여러 프로젝트가 공통으로 사용하는 자산을 둔다.

세부 역할:
- `shared/crop_data`
  - 공통 pre-crop 자산의 목표 위치
- `shared/schemas`
  - 공통 JSON 응답 포맷, annotation schema, output schema
- `shared/prompts`
  - 공통 설명 프롬프트, 출력 템플릿, 서비스용 프롬프트
- `shared/references`
  - 외부 기준 문서, 태스크 공통 참고자료

한 문장 책임:
- `shared`는 **도메인별 프로젝트를 넘어서 재사용 가능한 공통 자산만 보관하는 계층**이다.

주의:
- 실험 전용 코드나 빠르게 변하는 task config는 여기 넣지 않는다.
- `shared`는 최소 공통만 허용한다.

### 4-3. `projects`
- 실제 분석 과제를 수행하는 하위 프로젝트 집합을 둔다.

세부 역할:
- `projects/wrinkle`
  - 주름 분석 전용 프로젝트
- `projects/diagnosis`
  - 피부질환 진단 전용 프로젝트
- `projects/condition`
  - 피부컨디션 분석 전용 프로젝트
- `projects/pore_pigment`
  - 모공/색소 분석 전용 프로젝트
- `projects/elasticity_sagging`
  - 탄력/처짐 분석 전용 프로젝트

한 문장 책임:
- `projects`는 **분석 도메인별로 독립 실행 가능한 실험/서비스 단위를 담는 계층**이다.

### 4-4. `integration`
- 하위 프로젝트의 결과를 묶어 실제 사용 흐름으로 연결하는 계층을 둔다.

세부 역할:
- `integration/web`
  - UI, 업로드, 결과 렌더링, 중간평가 화면
- `integration/api`
  - 주름/진단/추후 과제를 묶는 상위 API 또는 orchestration
- `integration/evaluation`
  - 통합 시나리오 평가, cross-task 검증, 사용자 평가 로그

한 문장 책임:
- `integration`은 **여러 분석 프로젝트를 실제 서비스 흐름으로 묶는 통합 계층**이다.

### 4-5. `archive`
- 현재 실사용 기준에서는 종료되었지만 기록 보존 가치가 있는 과거 프로젝트를 둔다.

세부 역할:
- `archive/Skin_Proj`
  - 과거 VLM 기반 실험 프로젝트 보관

한 문장 책임:
- `archive`는 **삭제하지는 않되 현재 활성 구조에서 분리해야 하는 과거 자산을 보관하는 계층**이다.

## 7. `integration/web/api/evaluation`의 단계적 생성 원칙
### 7-1. `integration/web`
- 가장 먼저 생성한다.
- 이유:
  - 내일 진행할 주름 + 진단 통합 PoC의 핵심이기 때문
  - 사용자 입력/결과 표현 구조를 먼저 검증해야 하기 때문

### 7-2. `integration/api`
- 웹에서 실제로 다중 분석 결과를 호출·조합할 필요가 생길 때 생성한다.
- 즉시 과대 설계하지 않는다.

### 7-3. `integration/evaluation`
- 웹 결과가 어느 정도 안정화된 뒤 생성한다.
- 목적:
  - 통합 시나리오 평가
  - task 조합 품질 검증
  - 사용성/일관성 검토

원칙:
- 생성 순서는 `web -> api -> evaluation`
- 필요가 생길 때 단계적으로 만든다.
- 빈 폴더만 먼저 크게 만들지 않는다.

## 8. 문서 구조와 코드 구조의 대응 원칙
- 상위 문서 구조는 향후 코드 구조와 가능하면 1:1로 대응시킨다.
- 최소 대응 대상:
  - `docs/current`
  - `projects/<domain>`
  - `integration/<layer>`
  - `shared/<asset>`

예:
- `docs/current/001~004` 주름 문서군은 나중에 `projects/wrinkle` 구조와 대응되어야 한다.
- `projects/diagnosis` 정리 시에도 상위 문서가 코드 폴더와 대응되게 맞춘다.

## 9. 과설계 방지 원칙
- `shared`에는 아직 불안정한 실험 전용 코드/설정을 넣지 않는다.
- `projects`는 현재 살아 있는 프로젝트부터 순차적으로 정리한다.
- `integration`은 내일 PoC에 필요한 범위까지만 먼저 사용한다.
- 즉, 본 문서는 **확장 가능 구조를 정의하지만 오늘 모든 것을 물리적으로 구현하는 문서는 아니다.**
